- **계획으로만 표시:** 실제 위치 수집과 입력 진위 검증, 운영 C/Wallet·Preprod 연결, 보험사 시스템 연동, 자동 강제 반영, Rule 이전, 대량 처리 비용·성능, 이의 처리, 완성된 가입자·보험사 UX. 이들이 미구현이라는 사실 자체를 현재 모의 운행·로컬 증명 데모의 결함으로 세지 않는다.
- **사업 질문으로 답변:** 보험사 도입 수요·지불 의사·가입자 유인·가격은 검증 전 가설이다. 인터뷰나 비용 수치를 지어내지 않고, 데모의 기술 성과를 사업 검증 완료로 확장하지 않는다. 약관 문서의 LLM 변환은 데모 필수 경로가 아니며 보험사의 수기 Rule 입력·검토·승인을 사용한다.

## 이 Deck이 답해야 할 질문

1. 어떤 문제를 해결하는가? 보험사가 안전운전 할인을 판단할 근거는 필요하지만 가입자의 상세 주행기록 전체를 받을 필요는 없다.
2. 누가 무엇을 하는가? 보험사는 규칙을 검토·승인하고, 가입자는 수집 시작과 최종 결과 제출을 승인하며, 수집된 운행은 모두 누적 반영하고 보험사는 검증된 최종 결과를 보고 적용 여부를 결정한다.
3. 왜 Midnight인가? 수집되어 제출된 기록을 공개하지 않으면서 **승인 Rule, Dataset 입력, 이전 확정 State, 새 누적 State, 최종 결과** 사이의 계산 관계를 Compact로 검사한다.
4. 무엇을 공개하는가? 공개 원장에는 binding·commitment·Dataset Root·nullifier와 일부 처리 메타데이터가 남는다. 보험사가 받을 정확한 점수·거리 등은 별도 결과 opening과 권한 확인이 필요하다.
5. 실제로 어디까지 동작하는가? 로컬 증명·두 운행 상태 전이·최종 평가의 검증 근거와, 아직 연결되지 않은 제품/운영 경로를 구분한다.

Deck 전체에서 다음 세 상태를 혼동하지 않는다: **증명 유효 ≠ 할인 조건 충족 ≠ 보험사의 할인 적용 결정**. 300km·92점은 거리 조건을 충족하지 않아도 올바른 계산의 증명은 유효할 수 있다.

## 권장 본편: 8장 + 비교 장 1장(선택)

각 장의 `발표 포인트`는 외울 대본이 아니라 설명할 사실이다. 실제 Slides에는 문장을 줄이고 그림·숫자·상태 표기를 우선한다.

### 1. 프로젝트 한 문장

- **목적:** Drivacy의 대상, 문제, Midnight의 역할을 10초 안에 알린다.
- **화면:** 프로젝트명, “상세 주행기록을 보험사에 제공하지 않고 안전운전 할인 조건의 계산을 검증”한다는 한 문장, `가입자 → Drivacy/Midnight → 보험사`의 간단한 흐름.
- **발표 포인트:** 보험사에 주행 원본을 보내는 대신, 보험사가 승인한 조건으로 계산한 결과를 검증할 수 있게 한다. 이번 시연은 보험사 한 곳, 특약 한 종, 모의 주행을 대상으로 한다.
- **주의:** 영지식증명만으로 실제 보험 할인이 자동 결정된다는 인상을 주지 않는다.
- **근거:** [프로젝트 방향](../PROJECT_DIRECTION.md), [README](../README.md).

### 2. 문제와 정보 공개의 필요성

- **목적:** “왜 일반 DB 계산만으로 충분하지 않은가?”에 답한다.
- **화면:** 왼쪽에 상세 기록(경로·위치·정확한 운행시각·구간별 속도·개별 이벤트), 오른쪽에 보험사의 판단에 필요한 최소 결과(점수·누적 거리·조건 충족·검증 연결정보)를 둔다.
- **발표 포인트:** 할인 조건 검토에 원본 전체를 공유하면 가입자의 이동 정보가 과도하게 노출된다. Drivacy의 목표는 수집된 운행을 모두 누적 반영한 Dataset의 계산을 검증하면서 보험사에는 상세 원본을 전달하지 않는 것이다. 현재 강제 반영과 DB 원본 삭제는 구현·검증이 더 필요하다.
- **주의:** 이 문제 제기는 보험사가 결과 숫자를 전혀 받지 않는다는 뜻이 아니다. 정확한 점수·거리 공개는 현재 채택한 제품 방향이다. Drivacy의 계산·증명 처리 영역에는 원본이 일시적으로 존재할 수 있다.
- **근거:** [검증과 정보 공개 경계](../PROJECT_DIRECTION.md), [상태 전이 증명 문서](STATE_TRANSITION_PROOF.md).

### 3. 사용자 흐름과 각자의 결정

- **목적:** 기술 설명에 앞서 DApp 사용 흐름을 이해시킨다.
- **화면:** 아래 순서의 6개 장면. 구현된 화면이 없으면 실제 화면처럼 보이는 완성 UI 스크린샷 대신 **계획 흐름도**라고 표시한다.

  1. 보험사가 데모 Rule 값을 수기로 입력·검토·승인한다. 문서 변환이나 LLM 초안은 시연 필수 경로가 아니다.
  2. 가입자가 본인 보험계약·특약을 선택한다.
  3. 가입자가 반영할 모의 운행을 시작한다. Backend는 이전 확정 State와 등록 Rule을 기준으로 운행 입력을 고정한다.
  4. 운행별 증명과 실제 체인 반영을 확인한 뒤 새 누적 State를 확정한다. 실패·미확정이면 이전 확정 State를 유지한다.
  5. 가입자가 공개될 결과를 확인하고 제출을 승인한다.
  6. 보험사가 결과·검증 근거를 확인하고 할인 적용 또는 미적용을 결정한다.

- **발표 포인트:** 가입자의 결과 제출 승인과 보험사의 할인 결정은 별개다. `처리 완료`는 보험사가 적용 여부를 결정한 뒤의 상태다.
- **현재 상태:** 인증·계약/특약·Rule 관리·모의 운행 세션 등 Backend 기반이 있다. 이 6개 장면을 제품 UI와 운영 Midnight 연결로 완주하는 흐름은 제출 시점에 별도로 확인해야 한다.
- **근거:** [계획한 데모](../README.md), [모의 주행 설계](DRIVING_SIMULATION.md), [운행 서비스](../apps/backend/src/driving/driving-service.ts).

### 4. 두 운행으로 보는 누적 계산

- **목적:** 이전 State를 이어받는 이유를 숫자로 보여준다.
- **화면:** 작은 표 또는 두 단계 카드. `누적 거리`, `누적 이벤트`, `점수`, `조건`, `예상 할인율`을 같은 위치에 놓는다.

| 시점 | 누적 거리 | 누적 이벤트: 과속/급가속/급제동 | 점수 계산 | 조건·예상 할인 |
| --- | ---: | ---: | --- | --- |
| 첫 운행 후 | 300,000m | 2/1/1 | 100 − (2×2 + 1×1 + 1×3) = 92 | 500km 미만; 조건 미충족·0% |
| 두 번째 운행 후 | 550,000m | 3/1/2 | 100 − (3×2 + 1×1 + 2×3) = 87 | 500km 이상·80점 이상; 예상 10% |

- **발표 포인트:** 첫 번째 운행의 결과가 체인에서 확정돼 두 번째 운행의 이전 State가 된다. 과거 원본 기록 전체를 다시 넣어 누적 점수를 만드는 구조가 아니다. 0점 하한을 포함해 누적 이벤트에서 점수를 다시 계산한다.
- **주의:** 500km·감점 계수·할인율은 교체 가능한 **데모용 임시 Rule**이고 실제 보험상품 약관을 대표하지 않는다. 예상 할인과 보험사의 최종 적용은 구별한다.
- **근거:** [Core 계산](../packages/core/src/calculation.ts), [데모 산식과 근거](../PROJECT_DIRECTION.md), [상태 전이 문서의 손계산](STATE_TRANSITION_PROOF.md).

### 5. Midnight 구현: 무엇을 실제로 검사하는가

- **목적:** 기술 심사의 핵심 장. Merkle Tree와 Compact 회로가 각각 맡는 일을 보여준다.
- **화면:** 다음 관계를 한 그림에 표시한다.

```text
보험사 승인 Rule ── Rule Hash ──────────────┐
이번 운행 기록 ── Dataset Merkle Root ──────┤
최신 이전 확정 State ── State Commitment ───┼─ Compact 검사 ─→ 새 State Commitment
기록별 포함 경로·순번·집계값 ───────────────┘
```

- **발표 포인트:**
  - `initialize`: 0회 운행·0집계의 Genesis와 고정 Rule/Scope를 확인한다.
  - `beginTrip`: 최신 이전 State, 이번 Root, 목표 State, 기록 수를 고정한다. 이때 확정 State는 아직 바뀌지 않는다.
  - `appendRecord`: 기록의 Merkle 포함 경로뿐 아니라 **기록 순번 = 경로 위치 = 처리 cursor**를 확인하고 그 기록의 지표를 누적한다.
  - `finishTrip`: `cursor = recordCount`, 누적 합계와 후보 결과의 일치를 확인한 뒤에만 새 State를 확정한다.
  - `submitEvaluation`: 최신 확정 State로 결과 commitment를 만들고 같은 평가의 중복 제출을 nullifier로 막는다.
- **핵심 이유:** Merkle 포함만 확인하면 “어떤 기록이 묶음에 있다”는 사실은 알 수 있어도 모든 기록의 합계와 승인 규칙 계산이 맞는지는 알 수 없다. 회로가 순서·전체 처리·누적 계산까지 검사한다.
- **보여줄 코드:** [Compact 계약](../contracts/driving-state.compact)의 `checkRule`, `checkResult`, `beginTrip`, `appendRecord`, `finishTrip`, `submitEvaluation`. Dataset을 구성하는 [State 어댑터](../packages/midnight/src/state-adapter.ts)와 계산 기준인 [Core](../packages/core/src/calculation.ts)를 보조 자료로 둔다.
- **주의:** Compact의 Rule Hash와 업무 DB의 보험사 승인·보험계약 권한을 연결하는 것은 Backend와 Adapter의 책임이다. 온체인 해시 비교가 보험사의 승인 절차 자체를 증명하지는 않는다.

### 선택 장. 다른 ZK 프로젝트와 비교: 무엇을 더 검증하는가

- **배치:** 5장 바로 뒤에 넣어 9장으로 발표하거나, 시간 제한이 있으면 발표자 보조 슬라이드로 둔다. 우열이나 최초 구현 주장이 아니라 **검증 대상과 제품 흐름의 차이**를 설명한다.
- **화면:** 아래 세 줄을 간결한 비교표로 줄이고, 마지막 줄에 Drivacy의 핵심 관계식을 크게 놓는다.

| 비교 사례 | 공개된 프로젝트가 검증하는 중심 대상 | Drivacy와 비교해 설명할 지점 |
| --- | --- | --- |
| [Midnight ZKLoan 예제](https://github.com/midnightntwrk/example-zkloan) | 비공개 신용점수·소득 등으로 대출 자격과 한도를 평가한다. 현재 예제에는 신용 데이터 공급자의 암호학적 attestation도 있다. | Drivacy는 단일 자격 판정을 넘어 **운행별 기록 묶음 → 누적 집계 → 이전/새 State → 최종 보험사 제출 결과**의 순차 관계를 다룬다. 반대로 현재 Drivacy는 실제 주행 출처의 attestation을 구현·증명하지 않는다. |
| [Midnight Sea Battle 프로젝트](https://github.com/bricktowers/midnight-seabattle) | 비공개 게임판과 게임 규칙에 따른 턴·상태 전이를 검사한다. | Drivacy는 비공개 상태 전이 패턴을 **보험사가 승인한 산식·Dataset Merkle 포함/순서·누적 평가기간**에 연결한다. 게임 프로젝트가 상태 전이를 다루지 않는다고 주장하지 않는다. |
| **Drivacy의 현재 Compact 계약** | 승인 Rule Hash, 최신 이전 State commitment, 이번 Dataset Root와 기록별 포함·순번·집계값, 새 State 결과, 최종 평가 nullifier를 검사한다. | 개별 기록이 Root에 속한다는 사실만이 아니라 **그 기록들을 빠짐없이 정해진 순서로 더해 승인 산식의 결과와 일치하는지**가 발표의 핵심이다. |

- **발표 포인트:** “ZK로 개인정보를 숨긴다”는 공통점보다, **무엇을 검증 가능한 결과로 바꾸는지**를 말한다. Drivacy의 입력은 수집 후 제출된 여러 운행의 기록이고, 결과는 보험사 Rule에 따른 **시간을 이어가는 누적 상태**다. 첫 운행 300km·92점은 거리 미달이어도 유효한 계산이며, 두 번째 운행 550km·87점에서 예상 10%가 나온다는 사례로 차이를 설명한다.
- **보여줄 코드:** [Dataset leaf·경로·순번 검사](../contracts/driving-state.compact)의 `hashRecord`, `pathRoot`, `appendRecord`; [누적 상태 확정](../contracts/driving-state.compact)의 `beginTrip`, `finishTrip`; [최종 평가](../contracts/driving-state.compact)의 `submitEvaluation`. [독립 Core 계산](../packages/core/src/calculation.ts)과 [로컬 실행 증거](evidence/final-evaluation-2026-09-20.json)를 보조 근거로 둔다.
- **정확한 한계:** 다른 프로젝트에 이런 조합이 전혀 없다고 주장할 조사 근거는 없다. Drivacy의 ZK는 실제 주행 발생, 미제출 운행, 외부 센서의 진위를 보장하지 않는다. ZKLoan의 attestation은 오히려 이 데이터 출처 경계를 설명할 때 참고할 수 있다. 비교 사례 설명은 각 프로젝트가 공개한 [ZKLoan 저장소](https://github.com/midnightntwrk/example-zkloan)와 [Sea Battle 저장소](https://github.com/bricktowers/midnight-seabattle)를 기준으로 하고, 대회 전체 출품작의 독창성 순위를 뜻하지 않는다.

### 6. 프라이버시: 누가 무엇을 볼 수 있는가

- **목적:** “영지식인데 점수·거리가 보이나?”라는 질문에 명확히 답한다.
- **화면:** `공개 원장 / 보험사에 허용할 결과 / Drivacy 계산·증명 영역`의 3열 표.

| 영역 | 데이터와 검증 역할 |
| --- | --- |
| 공개 원장 | Rule·Scope·owner binding, State·결과 commitment, Dataset Root, nullifier, 기록 수·cursor·revision 등 처리 메타데이터. 정확한 거리·점수·개별 이벤트·원본·salt는 ledger에 저장하지 않는다. |
| 보험사 | 가입자 승인에 따라 제공하는 정확한 점수·거리, 조건 충족 여부, 예상 할인율과 검증 연결정보. 비공개 결과 opening을 공개 `resultCommitment`와 대조하고 실제 계약·체인 receipt·권한도 확인해야 한다. |
| Drivacy 처리 영역 | 원본 기록을 계산·증명 및 실패 복구에 일시적으로 사용할 수 있다. 원본 보관·삭제는 Backend/Storage 운영 책임이며 ZK 자체가 삭제 사실을 증명하지 않는다. |

- **발표 포인트:** salt를 포함한 commitment는 작은 범위의 점수나 거리 값을 단순 대조해 추측하기 어렵게 한다. 공개 처리 메타데이터까지 숨기는 구조는 아니다.
- **근거:** [Compact 공개 ledger](../contracts/driving-state.compact), [최종 평가와 결과 opening](FINAL_EVALUATION.md), [결과 opening 검증 코드](../packages/midnight/src/evaluation.ts).

### 7. 시연: 정상 사례와 거부 사례

- **목적:** 설계가 아니라 실행 가능한 증거를 보여준다.
- **화면:** 정상 흐름은 `Genesis → 첫 운행 확정 → 두 번째 운행 확정(revision 2) → 최종 평가 proof/result commitment/nullifier`를 보여준다. 거부 흐름은 기록 누락·순번 변경·오래된 이전 State·결과 변경·중복 평가 중 시연 가능한 한 가지를 선택한다.
- **발표 포인트:** 정상 예시의 550km·87점·예상 10%를 손계산 표와 연결한다. 거부 장면에서는 **어느 단계가 거부했는지**를 표시한다: 호스트 입력 검사, Compact proof, 체인 중복 검사, Backend 권한/확정 검사 중 하나다. 서로 다른 거부 단계를 모두 “ZK가 막았다”고 묶지 않는다.
- **보여줄 증거:** 실제 실행의 명령, 네트워크, 계약 주소 또는 receipt, State commitment/revision, 최종 result commitment/nullifier. 원본·비밀 opening·월렛 키는 화면이나 Deck에 넣지 않는다.
- **현재 증거의 범위:** [2026-09-20 로컬 실행 증거](evidence/final-evaluation-2026-09-20.json)는 전체 ZK 컴파일·106개 테스트, 로컬 브라우저 월렛·격리 PostgreSQL, 두 운행 revision 2, 최종 평가/nullifier, 변조·중복 거부를 기록한다. `network: undeployed`인 로컬 증거다. 2026-09-21 최초 배포·Genesis 월렛 승인 경로 변경 후 `-SkipZk` 108개 테스트는 통과했으나 전체 `-Live -BrowserIntegration` 재실행은 당시 Docker 엔진 문제로 체인 단계에 도달하지 못했다. 제출 시점에 최신 Live 결과를 다시 확인한다.
- **근거:** [검증 기록과 실행 안내](FINAL_EVALUATION.md), [운행 작업·상태 조회](../packages/midnight/src/trip-job.ts), [체인 확인 후 DB 확정](../apps/backend/src/chain-state/chain-finalizer.ts).

### 8. 구현 상태·남은 연결·핵심 결론

- **목적:** 구현 근거를 정확하게 닫고 심사위원의 다음 확인 경로를 준다.
- **화면:** `로컬에서 검증`, `Backend에 구현`, `제출 전 연결·확인`을 구분한 표와 저장소/데모 링크.

| 구분 | 표시할 항목 |
| --- | --- |
| 로컬에서 검증 | Compact 증명·두 운행 누적·최종 평가/nullifier, 로컬 브라우저 월렛 및 격리 DB 하네스. 변경 후 다시 실행해야 하는 부분은 날짜를 표시한다. |
| Backend에 구현 | 인증·본인 계약/특약, Rule 관리·검토용 Draft, 모의 운행 생성·세션, 등록·복구·DB 확정의 일부 서비스 경계. Fake Adapter/주입된 C 경계 검증을 운영 체인 통합으로 표시하지 않는다. |
| 제출 전 연결·확인 | 제품 UI, production C Adapter와 실제 체인 등록·상태 조회, 월렛 승인, 보험사 결과 전달·결정, 실제 네트워크/배포, 새 클론 재현성. 완료 여부는 제출 직전에 다시 확인한다. |

- **발표 포인트:** 가장 중요한 성과는 기록의 포함 여부만이 아니라 **승인 Rule에 따른 누적 계산과 최신 State 전이까지 연결한 증명**이다. 다음 단계는 이 로컬 기술 경로를 가입자·보험사 제품 흐름에 안전하게 연결하는 것이다.
- **주의:** 현재 Compact 배포 생성자는 Rule Hash를 고정한다. Backend의 Rule Version 갱신 오케스트레이션/Fake Adapter 검사만으로 온체인 Rule 갱신과 누적 State 유지가 운영 구현됐다고 표시하지 않는다. [계약 생성자](../contracts/driving-state.compact), [등록 서비스](../apps/backend/src/rule-registration/rule-registration-service.ts)를 함께 확인한다.
- **근거:** [README의 최신 상태](../README.md), [방향·미구현 경계](../PROJECT_DIRECTION.md).

## 발표 질문에 대비할 짧은 답의 기준

| 예상 질문 | 답변에 반드시 들어갈 점 |
| --- | --- |
| “원본이 진짜 운행인지도 증명하나요?” | 아니다. 수집되어 제출된 Dataset의 기록·계산·상태 관계를 검증한다. 실제 운행 발생과 수집 전 운행의 포착은 별도 데이터 출처 문제다. |
| “보험사는 아무 정보도 못 보나요?” | 상세 경로·위치·정확한 시각·구간별 기록은 제공하지 않는 방향이다. 가입자 승인에 따라 정확한 점수·거리 및 최소 결과를 제공할 수 있다. |
| “Merkle Root만으로 점수가 맞나요?” | 아니다. 기록별 포함·순번·전체 처리와 누적 산식을 Compact에서 검사한다. |
| “다른 ZK 프로젝트와 무엇이 다른가요?” | 공통 프라이버시 기술보다 검증 대상이 다르다. Drivacy는 수집 후 제출한 운행 Dataset의 모든 기록을 승인 Rule의 누적 계산, 최신 이전 State, 새 State, 최종 제출 결과에 연결한다. 비교 사례에도 비공개 조건 평가나 상태 전이가 있으므로 그것만 독점적 차별점이라고 말하지 않는다. |
| “증명이 성공하면 할인도 승인되나요?” | 아니다. 조건 충족과 예상 할인은 검증 결과이고, 적용·미적용은 보험사의 별도 결정이다. |
| “같은 결과를 다시 신청하면?” | 같은 확정 State의 평가 nullifier 재사용을 온체인에서 거부한다. 새 확정 State에 대한 재신청 정책과 심사 중/적용 완료 차단은 Backend 업무 상태도 필요하다. |
| “실제 제품과 네트워크에서 모두 작동하나요?” | 확인된 로컬 실행, Backend 구현, 제품/운영 연결의 최신 상태를 구분해 답한다. 2026-09-20 증거를 이후 변경의 검증으로 확대하지 않는다. |
| “원본은 언제 삭제되나요?” | 체인·DB 확정 후 삭제하고, 반복 실패는 체인 미반영·안전 종료 확인 뒤 즉시 삭제 대상으로 전환한다. 결과가 불명확한 동안은 보존해 조회한다. DB 원본 정리는 새 migration 적용이 필요하며 ZK는 삭제 사실이나 물리적 완전 소거를 증명하지 않는다. |

## Slides 제작·발표 전 점검

- [ ] 각 슬라이드에 **구현 확인 / 로컬 검증 / 계획** 중 해당 상태와 근거 날짜를 표시했다.
- [ ] 본편의 정상 숫자가 모두 `300km·92점 → 누적 550km·87점·예상 10%`로 일치한다.
- [ ] 보험사의 **할인 적용 결정**과 `expectedDiscountBps`를 다른 상태로 표시했다.
- [ ] 공개 원장의 `recordCount/cursor/revision` 등 메타데이터 노출을 숨기지 않았다.
- [ ] Rule Hash, Dataset Root, 이전 State, 기록별 누적, 새 State의 관계를 하나의 그림으로 설명했다.
- [ ] 비교 장을 쓰면 다른 프로젝트의 실제 공개 기능을 정확히 적고, Drivacy에 없는 외부 데이터 attestation이나 제품 통합을 차별점으로 주장하지 않았다.
- [ ] proof 성공·체인 receipt·DB 확정·원본 삭제를 서로 다른 단계로 표시했다.
- [ ] 로컬 `undeployed` 실행 증거를 Preprod 또는 실제 가입자 제품 E2E로 표현하지 않았다.
- [ ] 2026-09-21 변경 후 Live 재검증 여부를 제출 시점에 확인해 증거 날짜를 갱신했다.
- [ ] 발표용 정상·거부 데모가 실패해도 설명할 수 있도록 **실제 실행에서 얻은** 로그/화면 캡처를 준비했다. 캡처에 원본·secret·키가 없는지 확인했다.
- [ ] Slides, 제출 폼, README가 같은 구현 상태와 실행 방법을 말한다. 특히 [README의 오래된 첫 수직 기능 설명](../README.md)과 후반부의 최신 구현 설명이 충돌하는지 다시 확인했다.
- [ ] 실제 Google Slides 링크와 심사위원 열람 권한, 발표 계정의 접근 권한을 확인했다. 현재 이 문서에는 Slides URL이 없다.
