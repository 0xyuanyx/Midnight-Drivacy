# 운행 시작 버튼 기반 모의 주행 설계

작성일: 2026-09-18 (KST)

이 문서는 문서 업로드 대신 백엔드에서 모의 주행기록을 생성하는 방향을 정리한다.
생성기·운행 시작 API·진행 화면의 구현 완료 보고가 아니다.

## 이번에 정리한 방향

- 가입자가 `운행 시작`을 누르면 백엔드에서 합리적인 범위의 모의 주행기록을 생성한다.
- 승인된 할인 규칙의 최소 거리와 이전 확정 누적 거리를 읽어 데모 운행 거리를 정한다.
- 운행 거리·시간·과속·급가속·급제동 횟수를 생성하고 기존 Core 계산 및 증명 경로에 연결한다.
- 두 번 이상의 운행은 직전 확정 State에서 순차적으로 이어간다.
- 모의 주행임을 화면에 표시한다. 실제 GPS·지도·외부 내비게이션 연동은 추가하지 않는다.

구체적인 난수 범위·발생 확률·화면 재생 시간은 아래의 추천안이며 최종 확정값이 아니다.
보험사 약관 입력·규칙 승인 방식은 이번 변경의 대상이 아니다.

## 사용자 흐름

1. 가입자가 특약을 선택하고 모의 주행 수집을 활성화한다.
2. `운행 시작` 요청을 보낸다.
3. 백엔드가 본인 계약·평가기간, 등록된 승인 Rule, 이전 확정 State를 확인한다.
4. 해당 운행의 구간 기록을 한 번 생성하고 재처리할 수 있도록 비공개로 보관한다.
5. 화면에는 모의 거리·운행시간 증가와 이벤트 발생을 표시한다.
6. 운행 종료 후 생성 기록을 Core 계산 및 Dataset/Merkle·상태 전이 증명 경로에 전달한다.
7. 필요한 월렛 승인을 거쳐 검증·체인 반영을 확인한 뒤 B가 DB 누적 상태를 확정한다.
8. 가입자에게 이번 운행 결과와 누적 거리·점수·예상 할인 조건 충족 여부를 표시한다.

화면의 재생 완료와 계산·증명·체인 확정은 별개다. 검증 중이나 승인 대기 상태를 완료로 표시하지 않는다.

## 할인 거리 조건에 맞춘 생성 — 추천안

최소 거리를 고정된 `500km`로 넣지 않고 승인 Rule의 `minimumDistanceM`을 읽는다.
이전 누적 거리는 `previous.state.totals.distanceM`에서 읽는다.

누적 0에서 시작하고 최소 거리가 500km인 발표용 두 운행의 예시:

| 항목 | 첫 운행 | 두 번째 운행 |
| --- | --- | --- |
| 거리 생성 | 최소 거리의 50~60%: 250~300km | 두 운행 합계 목표를 최소 거리의 100~110%: 500~550km로 정하고, 이전 확정 누적 거리를 뺀 거리 생성 |
| 예시 결과 | 280km | 245km → 누적 525km |
| 시간 예시 | 평균 80km/h로 약 3시간 30분 | 평균 70km/h로 약 3시간 30분 |
| 거리 조건 | 미충족 | 충족 |

이는 거리 조건에 도달하는 과정을 보여주는 **장거리 모의 주행 시나리오**다.
운행마다 실제로 몇 시간을 기다리지 않고 화면에서 짧게 재생한다.
실제 대기시간과 모의 운행시간은 구분해서 표시한다.

두 번째 운행의 거리는 첫 운행의 화면 표시값이 아니라 체인 반영 후 확정된 정확한 거리로 정한다.
이미 거리 조건을 충족했다면 추가 운행은 일반 모의 주행 범위로 생성하고 누적값을 유지한다.
최소 거리 0 등 비례 범위가 성립하지 않는 규칙은 일반 주행 범위를 사용한다.
일반 주행 범위와 비율은 생성기 구현 시 정한다.

**거리 조건 충족과 할인 가능은 별개다.** 이벤트에서 계산된 점수가 기준에 미달하면 할인 조건은 미충족이다.
원하는 할인 결과에 맞춰 점수를 직접 만들거나 이벤트를 다시 뽑지 않는다.

## 서로 말이 되는 거리·시간·이벤트 — 추천안

거리·시간·이벤트를 각각 독립 난수로 뽑지 않고 하나의 주행 유형에서 연결해 생성한다.

1. 도심·고속도로·혼합 등 주행 유형과 목표 거리를 정한다.
2. 목표 거리를 소수의 구간으로 나누고 유형에 맞는 평균 속도를 생성한다.
3. 구간 거리와 평균 속도로 시간을 계산해 정수 초로 저장한다. 구간 거리 합은 목표 거리와 일치시킨다.
4. 구간 거리·시간·유형에 따라 낮은 확률로 과속·급가속·급제동 이벤트를 생성한다.
5. 짧은 구간에서 이벤트가 과도하게 발생하지 않도록 발생 간격과 상한을 둔다.

평균 속도만으로 과속 여부를 판단하지 않는다. 이벤트 횟수는 모의 이벤트로 생성하며
실제 센서 속도에서 탐지한 값으로 표현하지 않는다. 일반 감속은 감점 대상인 급제동과 구분한다.

속도·유형·화면 진행 정보는 생성기 내부 또는 가입자 화면용 정보다.
기존 Core 입력에는 아래의 구간 집계값만 전달하며 공유 계약 필드를 임의로 늘리지 않는다.
화면의 매 갱신을 증명용 구간으로 만들지 않고, 회로 처리 비용을 고려해 구간 수를 적게 유지한다.

## 기존 코드와 연결하는 위치

현재 코드에서 확인한 연결 기준:

| 코드 | 현재 역할 | 추가할 연결 |
| --- | --- | --- |
| [공유 계약](../packages/shared/src/bc-contract.ts) | `TripSchema`에 `source: simulated`와 구간 집계 입력이 있음 | 생성 결과를 기존 스키마로 검증 |
| [Core 계산](../packages/core/src/calculation.ts) | `calculateTrip`이 승인 Rule·이전 확정 State·이번 기록을 읽어 누적 계산 | 생성 기록을 `CalculateTripRequest`의 `trip`에 전달 |
| [상태 어댑터](../packages/midnight/src/state-adapter.ts) | Dataset·후보 상태와 실제 회로 연결 | 동일한 생성 기록으로 계산·Dataset·증명 입력 구성 |
| [운행 작업 제어기](../packages/midnight/src/trip-job.ts) | 작업·단계·월렛 승인·체인 상태 제어 | 기존 멱등·승인·재처리 경로를 유지 |

구간 입력은 `index`, `distanceM`, `durationSeconds`, `speedingCount`,
`accelerationCount`, `brakingCount`다. 거리 m·시간 초·이벤트 횟수는 음수가 아닌 정수다.
Trip에는 기존 계약에 따라 운행 ID와 `datasetSalt`도 필요하다.

생성 함수는 백엔드에서 구현할 수 있다. 기존 형식으로 생성하면 Core 산식을 바꿀 필요가 없다.
다만 생성기와 운행 시작 API는 추가 작업이며, 현재 코드가 이 사용자 흐름 전체를 제공한다는 뜻은 아니다.
API 경로·요청·응답·진행 조회 방식은 B의 외부 명세에 맞춰 정한다.

## 작업 범위

기존 A·B·C 분담에 맞춘 연결안:

- B: 운행 시작 요청의 인증·객체 권한, 승인 규칙·확정 상태 조회, 모의 기록 생성·보관, 작업 접수와 DB 확정.
- C: 생성 기록의 Core 계산·Dataset/Merkle·증명·체인 반영 확인 및 월렛 승인 인터페이스.
- A: 디자인 완료 후 시작 버튼·진행 표시·종료 결과·월렛 승인 화면 연결.

프론트 없이 생성기와 Core 연결부터 로컬에서 검증할 수 있다.
화면 없이 하는 생성·계산 검증과 실제 증명·체인·브라우저 월렛 E2E 검증은 구분해서 보고한다.

## 같은 운행의 재시도와 원본 처리

- 최초 요청에서 만든 기록·운행 ID·salt를 유지한다. 동일 요청 재시도에서 난수를 다시 돌리지 않는다.
- 화면도 처음 생성한 기록을 재생한다. 화면용 수치와 계산용 기록을 별도로 생성하지 않는다.
- 같은 평가 범위의 운행은 이전 운행 확정 후 다음 운행으로 이어간다.
- 원본은 기존 합의대로 실제 체인 반영 확인 후 삭제하며 누적 State·확인 이력은 유지한다.
- 실패·결과 불명의 보관·재처리는 기존 기준을 따른다. 생성 방식 변경으로 이 정책을 바꾸지 않는다.

## 구현 후 확인할 사항

- 생성한 구간 거리 합이 목표 거리와 일치하고 거리·시간·이벤트가 설정 범위 안에 있는지.
- 현재 500km 규칙뿐 아니라 다른 최소 거리와 이미 누적된 상태에서도 생성이 동작하는지.
- 두 운행이 직전 확정 State로 이어지고 표시값의 반올림이 조건 판정에 영향을 주지 않는지.
- 같은 요청을 재처리해도 기록이 바뀌거나 운행이 두 번 누적되지 않는지.
- 생성 기록이 기존 Core 입력 검증을 통과하고 점수는 승인 Rule로 계산되는지.
- 실제 증명 연결 후 실패·승인 취소·체인 결과 불명에서 이전 확정 상태를 유지하는지.

생성기 구현 검증에는 프로젝트의 별도 Linux 실행 환경·독립 기준 검증 원칙을 적용한다.
이번 문서 작성에서는 생성기·API·화면 코드를 구현하거나 실행하지 않았다.

## 증명이 확인하는 범위

검증 대상은 생성된 모의 기록에 승인 규칙을 적용한 계산과 이전·신규 누적 상태의 관계다.
실제 운행 여부나 전체 운행의 완전성을 증명하는 기능으로 설명하지 않는다.
보험사 공개 범위와 원본 비공개 원칙은 기존 설계를 유지한다.
