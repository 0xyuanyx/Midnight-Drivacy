## 채택한 기능별 분담

**A는 약관·LLM 규칙 초안, B는 서비스 Backend·데이터 처리, C는 Core 계산·Midnight 검증을 중심으로 맡는다.** A가 향후 프론트까지 맡는 점을 고려해 Backend 업무량을 세 사람에게 동일하게 배정하지 않는다. 주 담당은 기능 구현·테스트·문서·통합까지 책임지고, 연결 담당은 자기 영역에 영향을 주는 계약과 변경을 검토한다.

## 채택한 공통 작업 원칙

1. **요청 범위와 확정 수준:** 최신 사용자 지시와 확정 명세를 따른다. 제안·미정을 임의로 구현 사양으로 바꾸지 않는다. 신규 기능·사업 규칙은 이번 분담에서 추가하지 않는다.
2. **Git·변경 보존:** 새 브랜치를 만들지 않는다. 시작 전 실제 체크아웃·작업 변경을 확인하고 다른 사람의 변경을 덮어쓰지 않는다. 커밋·푸시는 별도 지시를 따른다. 커밋 시 Drivacy의 어떤 기능 변경인지 분명히 적는다.
3. **담당과 공유 파일:** 기능 담당자가 자기 변경을 끝까지 책임진다. 공통 API/스키마·DB 변경·의존성/lockfile·서버 진입점은 B가 조정하고 A·C는 필요한 변경을 먼저 공유한다. Compact·체인 어댑터와 생성 코드는 C가 조정한다. Rule/State 의미는 세 사람이 함께 합의한다. 같은 파일을 동시에 고치지 않는다. 기능 담당 구분은 새 브랜치나 별도 서버를 요구하지 않는다.
4. **계약 먼저:** 연결 기능은 요청·응답·오류, 상태와 단위를 먼저 맞춘다. 계약 변경 시 상대에게 알리고 관련 계산·회로·API·문서를 함께 맞춘다. 화면 편의를 위해 승인 규칙 또는 확정 상태를 바꾸지 않는다.
5. **승인 규칙과 상태:** 승인된 동일 규칙 버전을 계산·증명에 사용한다. 후보 상태와 확정 상태를 구분하고 체인 검증·반영 확인 후 확정한다. 실패·미확정 시 이전 확정 상태를 유지한다.
6. **권한·개인정보:** 인증과 객체 접근권한을 서버에서 검사한다. 가입자용 설명, 보험사 결과, 공개 원장 입력을 구분한다. 원본을 보험사 응답·공개 입력·일반 로그에 넣지 않는다. 가입자 개인키는 Drivacy 서버에 저장하지 않는다. 개인키·LLM 키를 소스·Frontend 번들·Git에 넣지 않고 LLM 키는 팀 서버 Secret/환경변수에서만 관리한다.
7. **실패와 삭제:** 증명·트랜잭션 실패 시 원본을 재처리 가능하게 보관하고 체인 반영을 확인한 뒤 삭제한다. 재처리·중복·동시 요청과 체인 성공 후 DB 반영 실패를 다룬다. 미정 보관기간·재시도 한도를 임의로 사업 정책으로 확정하지 않는다.
8. **완료의 증거:** 담당자는 정상·관련 실패 케이스를 확인한다. 계산 테스트, 계약 컴파일, 실제 증명·체인 반영, 월렛 승인, LLM 실제 호출, 배포·새 클론 실행을 각각 기록한다. mock 응답이나 해시 생성만으로 실제 검증 완료를 표시하지 않는다.

2026-09-18 후속 사용자 확정으로 검증·디버깅은 런타임·의존성·캐시를 분리한
별도 실행 환경에서도 진행한다. 계산은 구현을 보지 않고 명세에서 작성한 독립
기준 계산과 대조한다. 실패 원인 수정 후 영향받은 검사를 재실행하고 환경·명령·
소스 해시·결과·미검증 범위를 기록한다. 상세 기준은 PROJECT_DIRECTION의
`향후 검증 방식`을 따른다.
9. **데모·증명의 한계:** 모의 운행·임시 수치를 명시한다. 조건 미충족은 유효한 증명일 수 있다. 증명 유효와 보험사 할인 결정을 구분한다. 실제 운행·전체 기록의 완전성·삭제 사실까지 ZK가 보장한다고 주장하지 않는다.
10. **방향 기록:** 새로 합의한 방향은 날짜와 함께 PROJECT_DIRECTION에 결정/제안/미정을 구분해 반영한다. 구현·실행 상태가 바뀌면 README도 갱신한다. 현재 세션의 Midnight 도구 활성화 제한을 따른다.

## 프론트 없이 진행할 순서

1. 세 사람이 스택·실행 환경과 공통 Rule/State·API 계약을 정한다. C는 컴파일부터 실제 체인 반영까지의 작은 기술 경로를 확인한다.
2. A는 약관·LLM 초안 모듈, B는 인증·모의 계약·규칙 승인·서버 기반, C는 승인 Rule 기반 계산·Merkle·회로를 맡아 진행한다. 모듈 검증과 실제 배포·체인 검증은 구분한다.
3. A의 초안을 B가 승인·저장하고 C의 체인 규칙 등록·계산에 연결한다. B가 운행을 접수해 C의 계산·증명을 호출하고, 체인 반영 확인 후 한 운행을 확정한 뒤 두 번째 운행을 누적한다. 프론트 구현 전 SDK 승인 기술 검증과 향후 브라우저 승인 E2E는 구분한다.
4. B의 최종 신청을 C의 최종 상태 검증·nullifier와 연결하고 B의 보험사 결정까지 API로 확인한다.
5. 세 사람이 담당 기능의 조작·중복·실패·원본 삭제와 새 클론 실행을 확인한다. 디자인 완료 후 A의 프론트를 연결하고 C와 브라우저 월렛 승인, B와 전체 사용자 흐름을 검증한다.

이 순서는 구현 계획이다. 현재는 실행 가능한 앱·계약·월렛·LLM 서버가 없으며 이번 작업은 문서화다.
