## 사용자 흐름

대시보드 → 요청 선택 → 요청 정보/검증 결과/처리 이력 확인 → 가능한 업무 결정 → 상세·목록·KPI·이력 동시 갱신.

평가 요청 → 평가 선택 → 평가 결과/증명 검증/처리 이력 확인 → 할인 적용 또는 미적용 결정 → 완료 상태 확인 → 목록 복귀.

검증 실패는 이유와 가능한 다음 행동을 보여준다. 자동 승인이나 임의의 재검증 성공 전환은 하지 않는다. 뒤로가기와 메뉴 전환은 데이터 상태를 변경하지 않는다. 처리 완료를 열면 저장된 결과를 보여주며 결정 버튼을 다시 활성화하지 않는다.

## 구현된 코드 경계

`apps/web/src/app`은 공통 화면 조립과 URL 상태, `domain`은 요청·평가 상태 및 결정 전이, `data`는 실제 API로 교체 가능한 브라우저 localStorage fixture 어댑터를 담당한다. 로드·저장 실패와 저장 중 상태를 UI에서 구분한다. 현재 Backend에 확인된 업무 계약이 없어 실제 API는 연결하지 않았다. 새 라우팅·원격 상태 라이브러리를 추가하지 않고 History API와 React 상태만 사용한다.

## 인수 시나리오

1. 메뉴를 바꿔도 eyebrow/검정 제목/회색 설명의 시작선과 간격이 일치한다.
2. 요청 A→B를 선택하면 상세·탭·결정 대상 모두 B를 가리킨다.
3. 탭 전환과 브라우저 뒤로가기에서 요청 선택이 뜻밖에 바뀌지 않는다.
4. 정상 검증과 조건 충족이 있어도 담당자 결정 전 할인 적용 완료로 표시하지 않는다.
5. 결정 실패 시 완료 토스트/건수 증가가 없고 같은 입력으로 재시도 가능하다.
6. 이미 처리된 요청은 재결정되지 않으며 목록·상세·이력이 같은 결과다.
7. 0건, 검색 0건, 네트워크 오류, 권한 오류를 서로 다른 상태로 표시한다.
8. 긴 보험명·ID와 200% 확대에서 버튼/본문이 겹치지 않는다.
9. 창을 줄여도 핵심 정보와 행동에 접근할 수 있다.
10. 실제 API 연결 시 모바일 신청과 보험사 웹의 신청 ID·규칙·최종 결과가 일치한다. 독립 fixture 검증만으로 이 항목을 완료 처리하지 않는다.

## 현재 종료선

`apps/web` 독립 데모, 브라우저 저장·오류 상태를 포함한 상태 전이 테스트, 타입 검사, 프로덕션 빌드, 1512/1440/1280/1024 브라우저 검수를 완료했다. 외부 Figma 수정·배포·실제 API 쓰기·새 브랜치/PR 생성은 하지 않았다. 다음 단계는 계약 확정 후 fixture 어댑터를 실제 API 어댑터로 교체하고 모바일 신청 ID와 E2E 일치를 검증하는 것이다.
