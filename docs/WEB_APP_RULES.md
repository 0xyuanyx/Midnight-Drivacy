# Drivacy 보험사 웹 규칙

2026-09-23 추가 메뉴 구현: 특약 관리 안에 규칙 변경을 통합하고 검증 이력 검색·평가 요청 상세 이동과 읽기 전용 연동 상태 목업을 구현했다. 규칙 변경은 문서 업로드 → 추출 내용 확인·수정 → 규칙 초안 검토 순서다. PDF/DOCX/TXT/MD의 글자를 브라우저에서 읽고, 스캔 PDF처럼 추출할 내용이 없으면 직접 입력해 보완한다. 기존 화면의 셸·카드·목록/상세 배치를 유지한다. 자동 변환은 담당자 검토용 초안까지만 만드는 방향이며 현재 화면은 서비스 호출·초안 저장을 하지 않는다. 검증 이력의 현재 값은 브라우저 fixture이므로 실제 ZK/체인 검증 성공으로 표시하지 않는다.

2026-09-23 후속 연동: 웹의 모든 화면에서 같은 5개 메뉴를 사용한다. 로컬 연동 실행에서는 평가 요청이 앱의 데모 신청을 공유 브리지에서 조회하고, 검증 이력은 실제 ZK 미연결 상태를 표시한다. 대시보드 특약 승인 요청은 기존 웹 fixture 영역이며 앱의 할인 평가 신청과 합치지 않는다.

작성/갱신: 2026-09-23 · 상태: 독립 fixture 및 로컬 프론트 연동 데모 구현. 실제 보험 API·Midnight 연동·배포는 하지 않았다.

## 1. 기준과 범위

최신 사용자 결정 → 합의한 앱/웹 공통 원칙 → 이 문서 → Figma 순으로 판단한다. 2026-09-22 정밀 재현 요청에 따라 실제 Figma 측정값을 아래의 이전 제안값보다 우선한다. 앱에서 확정한 것은 역할별 타이포, 같은 화면 유형의 제목·행동 위치 일치, 상태 일관성이라는 원칙이다. 모바일 CTA의 화면 하단 고정을 PC 전체에 그대로 복사하지 않는다.

대상은 보험사 담당자의 요청 검토 웹이다. React + TypeScript + Vite와 기존 npm workspace 방향을 따른다. 앱은 React Native로 유지한다. 웹은 Vite 7.3.6, React 19.2.3, Vitest 3.2.7 기준으로 검증했다.

Figma에 빠진 로딩·빈 상태·긴 내용·작은 창·오류와 배치 불일치는 아래 규칙으로 보완한다. 서비스 흐름·권한·규칙값·공개 정보가 달라지는 개선은 제안으로 기록한다. 임의로 새로운 업무 기능을 추가하지 않는다.

## 3. 공통 화면 구조

두 업무 화면은 하나의 AppShell, PageHeader, SummaryGrid, RequestWorkspace를 공유한다. 업무마다 목록 열·상세 탭·행동만 바꾼다.

| 항목 | 제안 기본값 / 규칙 |
|---|---|
| 검수 기준 | 1512×927, 1440×900, 1280×800, 1024×768 |
| 사이드바 | 원본 실측 220px, 워드마크 x=30 / y=28, INSURER 바로 아래. 현재 구현은 통합 후 5개 메뉴 |
| 본문 | 원본 실측 좌우 32px, 위 22px |
| 페이지 제목 | 헤더 내부 공통 슬롯. 같은 viewport에서 모든 화면 시작점 동일 |
| 제목 묶음 | 페이지 eyebrow 없음. 제목 24px → 7px → 설명 12px. 상세에만 9px eyebrow |
| 헤더 이후 | KPI y=96 / 높이 103px. 대시보드 안내 배너 y=215 / 높이 54px. 다음 영역 간격 16px |
| 기본 간격 | 4 / 8 / 12 / 16 / 24 / 32 / 48px만 사용 |
| 목록·상세 | 남은 너비 2:3, gap 16px. 1512px에서 목록 x=252 / 상세 x=752.797 |
| 카드 | 바깥 패널 radius 14px / border 1px. 상세 padding 22px, 내부 카드 radius 12px |
| 표 | 목록 헤더 68px / 열 머리글 30.5px / 행 57px. 선택은 행 전체 연한 배경+테두리 |
| 버튼 | 데스크톱 기본 32px, 헤더 아이콘 34px, 목록 도구 27px. 원본 밀도 우선 |

페이지 전체를 주 스크롤로 삼고 중첩 스크롤은 표 가로 넘침 등 필요한 영역에만 둔다. 상세 패널 행동 영역은 패널 하단의 공통 슬롯으로 정의한다. sticky가 필요한 긴 상세에서는 해당 패널 안에서만 붙이고, 마지막 내용을 가리는지 확인한다. 조회/이력 탭에도 같은 구조를 유지하며 불가능한 작업은 이유를 표시한다.

960px 이하에서 목록→선택 상세를 단일 열로 전환하고 680px 이하에서 사이드바를 상단 내비게이션으로 바꾼다. 모바일 앱과 별개인 웹의 축소 대응이다. 중요한 열과 업무 행동을 숨기지 않는다.

## 4. 타이포·색상

웹은 원본 SVG의 Arial 계열 타이포를 사용하고 한국어 시스템 글꼴과 번들 Pretendard를 fallback으로 둔다. 모바일 Pretendard 규칙은 변경하지 않는다. 한 역할은 모든 화면에서 같은 font family, size, weight, line-height, letter-spacing을 사용한다.

| 역할 | 크기/줄높이 | 굵기 |
|---|---|---|
| 페이지 제목 | 24/29 | Bold |
| 상세 패널 제목 | 17/20 | Bold |
| 카드·섹션 제목 | 15/20 | Bold |
| 목록 이름 | 12/15 | Bold |
| 버튼 | 10/14 | Bold |
| 보조 설명·표 머리글 | 9–10/11–14 | Regular |
| 상세 eyebrow·상태 | 9/11–12 | Bold |
| KPI 숫자 | 27/31 | Bold |
| 점수 / 할인율 | 38/44, 29/34 | Bold |

숫자는 tabular-nums, 표 숫자 열은 오른쪽, 텍스트는 왼쪽 정렬한다. 한국어는 단어 단위 줄바꿈, ID/hash는 영역 내 줄바꿈과 복사 기능을 제공한다. 정보성 본문을 생략 부호만으로 숨기지 않는다.

실제 Body는 #F3F6FA, Surface #FFFFFF, Ink #182235, Secondary #68758A, Accent #2F6DF6, Border #E3E8F0, Sidebar #14213D다. 바깥 Figma 프레임의 #F5F7FB가 아닌 실제 Body 채우기를 따른다. 상태는 텍스트와 색을 병행한다.

## 5. 컴포넌트 계약

- AppShell: 로고, 내비게이션 선택 상태, 계정 영역. 선택 메뉴를 화면마다 직접 칠하지 않는다.
- PageHeader: eyebrow/제목/설명/보조 행동. 제목 높이에 맞춰 내용이 흐르며 화면별 margin 보정 금지.
- SummaryCard: 라벨/수치/보조문구. 임의 통계 수치 생성 금지.
- RequestList: 검색/필터/정렬/페이지/선택 ID. 목록 이동 후에도 선택과 필터를 복원한다.
- RequestDetail: 선택 요청 ID를 기준으로 데이터 조회. 없으면 안내, 유효하지 않으면 목록 복귀 제공.
- DetailTabs: 키보드 탭 전환, 선택 표시와 실제 패널 일치. 탭을 바꿔도 요청 ID 유지.
- FieldRow: 라벨과 값 공통 정렬, 긴 값은 줄바꿈. 요청 정보/검증 정보/이력에서 재사용.
- StatusBadge: 업무 종류와 상태의 명시적 매핑. '검증 유효'를 '승인 완료'로 바꾸지 않는다.
- ActionBar: 주요 행동 1개, 보조 행동, busy/disabled/reason. API 실패 시 입력과 선택 유지.
- AsyncState: 로딩/빈 목록/검색 결과 없음/불러오기 실패/권한 없음 분리.

컴포넌트의 default/hover/focus/pressed/disabled/loading을 정의한다. 단순 선택 변경에는 확인 모달을 넣지 않는다. 승인·반려 등 결정을 저장하는 행동은 대상과 결과를 보여주는 확인 단계 한 번을 거친다. 처리 중 중복 클릭을 막고, 서버의 최종 응답 전에는 완료 상태로 바꾸지 않는다.

## 6. 데이터와 화면 상태

요청 선택, 상세 탭, 검색·필터는 URL에 보존할 수 있게 설계한다. 상태별 별도 페이지를 복제하지 않는다. 목록·상세·KPI·이력은 같은 요청 엔티티에서 읽는다. 완료 후 다른 화면으로 가거나 새로고침해도 이전 승인 대기로 되돌아가면 안 된다.

업무 판정 상태와 증명 상태를 별도 필드로 표현한다. 기술 실패/검증 무효/유효하지만 조건 미충족/담당자 미적용은 구분한다. 오류 코드는 계약을 확인해 UI 문구로 매핑하며 존재하지 않는 API 이름을 만들어 연결하지 않는다.

보험사에는 허용된 최종 점수·거리·평가기간·규칙 버전·최소 검증 결과만 제공한다. 원본 위치·경로·구간별 속도·정확한 주행 시각은 표시·요청하지 않는다. 실제 계약과 권한 검사는 서버 책임이다.

수기 규칙 입력·검토 경로를 보존한다. 이번 웹 UI 작업으로 LLM/PDF/OCR 경로를 새로 추가하지 않는다. 목업 데이터는 별도 어댑터로 격리하고 실제 API·실제 증명과 구분한다. 모바일 AsyncStorage와 웹 localStorage만으로 두 제품이 연동된다고 주장하지 않는다.

## 7. 변경·완료 기준

- 같은 역할의 글자와 헤더 위치를 대표 두 화면에서 나란히 확인한다. 기준 창 크기에서 헤더 슬롯 좌표 차이 1px 이내를 목표로 한다.
- 승인 대기/검토 필요/처리 완료/검증 실패 전환에도 같은 구조와 행동 슬롯을 유지한다.
- 긴 이름·보험명·ID, 0건·1건·다수 행, 좁은 창, 확대, 오류를 확인한다.
- 검색→선택→탭 전환→결정→목록 복귀→새로고침까지 실제 브라우저에서 검수한다.
- 공통 컴포넌트 검수 전 전체 화면을 복제하지 않는다. 예외 스타일에는 이유와 적용 범위를 남긴다.
- 구현·테스트·실제 API 연결·실제 기기/브라우저 검수 범위를 구분해 보고한다.

## 8. 구현 착수 시 해소할 사항

1. 모바일 표시 550km와 프로젝트 승인 기준 500km 차이: 550km는 데모 최종 누적 거리이고 판정 최소 거리는 별개다. 웹은 승인 Rule 값을 사용하도록 설계한다. 앱 수정은 별도 후속 범위로 기록한다.
2. Figma의 특약 요청 승인/반려와 평가 결과 할인 적용/미적용은 별도 업무로 매핑한다. 특약 요청 승인을 곧 Rule Version 승인으로 단정하지 않는다.
3. 20개 원본 프레임의 시각 대조와 24개 브라우저 상태 조합 검수를 수행했다. 픽셀 단위 완전 동일로 표현하지 않고 측정 오차·업무 규칙 차이는 WEB_FIGMA_AUDIT에 기록한다.
4. `apps/web`은 독립 fixture 어댑터로 구현했다. 최신 코드 확인 결과 현재 Backend에는 이 화면의 요청/평가 목록 및 결정 저장 계약이 없으므로 실제 API 연결로 표현하지 않는다.
5. 사이드바 6개 항목을 모두 표시한다. 20개 프레임 밖 4개 항목은 범위 안내를 제공하며 실제 업무 화면은 대시보드·평가 요청 두 종류다.
