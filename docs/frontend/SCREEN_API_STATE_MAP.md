# 화면-API-상태 매핑표 (P3-1)

작성일: 2026-09-18 (KST). §1.1(`origin/feat` route 목록), `demo/index.html`(모의 HTML 프로토타입, 75줄), `docs/CLAUDE_CODE_A_WORK_PLAN.md` §3("Backend 접점과 디자인 전 프론트 준비")을 근거로 작성. 와이어프레임 URL은 열지 않았다(브리핑 §10 요약만 사용 — 이번 카드에서는 브리핑을 다시 열지 않고 §1.1·데모 HTML만으로 작성했으므로 와이어프레임 화면명·문구는 반영되지 않았을 수 있음, [확인 필요]).

라벨: `구현됨`(feat에 실제 route 존재) / `미구현`(feat에 route 없음, A 제안 필요) / `A 제안`(이 표에서 처음 제안하는 접점).

**공통 원칙(D1·D4, `docs/PLAN_DECISIONS.md`):** 모의 운행은 `시작→진행→검증/승인 대기→결과` 4단계로 표시하되, **"화면 재생 완료 ≠ 계산·증명·체인 확정"**이다(D1=제출 시 1회 증명이므로 운행 중에는 어떤 증명도 생성되지 않는다). **"증명 무효" ≠ "유효하나 조건 미충족"**을 모든 결과 화면에서 구분 표시한다. 점수·Rule 충족 여부·증명 상태는 프론트에서 판정하지 않고 Backend 응답 값을 그대로 표시한다.

## 3. B에게 필요한 route 목록 (미구현 정리)

1. 가입자용 "승인된 Rule 조회" GET route (화면 4) — 초안이 아닌 승인본만.
2. 모의 운행 시나리오/누적 계산 API 또는 명시적으로 "프론트 로컬 계산" 채택 여부 결정 (화면 5~6).
3. 신청 제출 API (화면 7).
4. 신청 상태 조회 API — 폴링 전략 포함 (화면 8).
5. 신청 결과 조회 API (화면 9).
6. 보험사 신청 목록/상세/이력/결정 API 4종 (보험사 화면 2~5) — 현재 feat에 INSURER 전용 route 자체가 없음(§1.1).
7. `POST /insurer/special-contracts/:id/rule-drafts`(P1-2 제안) 및 규칙 승인 API — 보험사 화면 1.

## 4. 데모 HTML(`demo/index.html`)과의 차이

데모 HTML은 서버 API 없이 브라우저 메모리(`state` 객체)만으로 전체 흐름(규칙 승인→모의 운행→제출→검증→결정)을 흉내낸다. 실제 프론트(`apps/web`, P3-2)는 위 표의 route를 통해 서버 상태를 반영해야 하며, 데모 HTML의 "모의 검증"·"모의 결정" 버튼처럼 클라이언트가 임의로 검증/결정 결과를 만들어내는 로직은 이식하지 않는다.

## 미검증 항목

와이어프레임 실제 화면 구성(브리핑 §10)은 이번 카드에서 열람하지 않아 반영되지 않음. 위 미구현 route는 모두 API 설계 제안이며 구현되지 않았다.
