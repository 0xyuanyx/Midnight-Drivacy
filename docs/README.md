## 확정한 제품·MVP 범위

- 대상은 2026 Midnight Korea Hackathon이다.
- 보험사가 승인한 기존 안전운전 특약 규칙을 적용한다. 새로운 운전점수 기준을 만드는 서비스가 아니다.
- 예시 보험사 한 곳·특약 한 종과 모의 주행데이터를 사용한다. 가입자가 수집을 활성화한 운행만 계산 대상이다.
- 가입자 모바일 중심, 보험사 PC 중심 반응형 웹을 목표로 한다.
- Frontend는 React를 사용하고 디자인 완성 후 구현한다. 현재 프로토타입은 구현 판단 대상으로 삼지 않는다.
- 이메일 기반 로그인과 역할 구분, 보험사·특약 선택, 가입자 임베디드 월렛을 MVP에 포함한다.
- 임베디드 월렛은 Midnight Wallet SDK를 사용하는 자체 보관형 구조다. 가입자 개인키는 서버에 저장하지 않는다. 보험사 사용자는 별도 월렛 설치 없이 이용한다.
- 약관 업로드 → LLM 규칙 초안 → 보험사 수정·검토 → 최종 승인 → Rule Hash 생성 → Midnight 등록 순서다. 승인 전 초안은 계산·증명에 적용하지 않는다.
- LLM 초안을 우선 시도하고 실패하면 수기 입력 후 동일한 검토·승인 경로를 사용한다. LLM이 구현되지 않으면 수기 경로를 유지한다.
- 클론한 앱의 기본 LLM 실행 방식은 **팀 배포 Backend 호출**로 확정했다. 심사위원에게 LLM 키 입력을 요구하지 않는다. [LLM 실행 설계](LLM_EXECUTION.md)를 따른다.
- 두 번 이상의 모의 운행을 순차 반영한다. 운행별 검증·체인 반영 후 신규 누적 상태를 확정한다.
- Dataset Merkle Tree를 MVP에 적용한다. Driver Merkle Tree는 필수 채택으로 확정하지 않았다.
- 가입자가 공개될 결과를 확인하고 제출을 승인한다. 보험사는 검증 결과와 최소한의 특약 판단 결과로 할인 적용·미적용을 결정한다.
- `처리 완료`는 보험사의 할인 적용·미적용 결정까지 끝난 상태다. `증명 유효`와 `할인 승인`은 별개다.
- 동일 평가 결과의 중복 제출은 Backend와 온체인 `nullifier`로 방지한다.
- 실제 GPS·외부 운행데이터·실제 보험사 운영 시스템 연동과 다중 기기 월렛 복구는 MVP 범위 밖이다.

## 상태 확정·정보 공개 원칙

1. 기존 확정 상태와 승인된 규칙 버전을 조회한다.
2. 신규 운행을 반영한 후보 누적 상태를 계산한다.
3. 필요한 증명과 커밋먼트를 생성한다.
4. Midnight에서 최신 이전 상태 일치와 상태 전이 관계를 검증한다.
5. 검증 및 체인 반영 확인 후에만 DB 신규 상태를 확정한다.
6. 실패·미확정 시 이전 확정 상태를 유지한다. 동시 요청·중복·재시도에도 한 운행을 두 번 반영하지 않는다.

DB를 먼저 확정하고 검증 실패 시 되돌리는 방식은 사용하지 않는다. 원본은 검증·트랜잭션 반영 확인 후 삭제하고, 실패하면 재처리를 위해 보관한다. 최종 신청은 최종 확정 상태를 사용한다.

보험사에 원본 위치·경로·정확한 운행시각·구간별 속도·개별 위험운전 기록을 전달하지 않는다. 유지할 정보는 문서에서 허용한 누적 집계값·점수·평가기간·상태 커밋먼트·규칙 버전·검증 연결정보 등으로 제한한다. 가입자 설명과 보험사 공개 범위는 구분한다.

ZK가 검증할 대상은 제출된 기록에 대한 승인 규칙 계산과 이전·신규 상태의 관계다. 실제 운행 발생, 전체 운행의 완전성, 미제출 운행, 원본 삭제 사실과 보험사의 결과 재사용 방지를 증명한다고 표현하지 않는다. 해시·커밋먼트 생성이나 REST 응답을 ZK 검증으로 표현하지 않는다. 원본은 Drivacy의 계산·증명 영역에 일시적으로 존재할 수 있다.

## API·작업 기준

우선순위는 최신 사용자 명시적 지시 → 최종 API 명세서·데이터 플로우 → 최종 기획 문서 → 기존 코드·주석 → 일반 개발 관행이다.

- 외부 API 경로·필드·상태·오류 규약은 확정 명세를 따른다. 내부 구현 필드는 외부 계약과 분리한다.
- 인증과 인가를 구분하고 역할·객체 단위 접근권한을 확인한다.
- 요청 접수와 실제 검증 완료를 구분하고, 명세에 따른 비동기·실패 상태와 멱등 처리를 적용한다.
- 기존 사용자 변경을 보존한다. 요청하지 않은 기능·사업 규칙·수치를 추가하지 않는다.
- 모의 데이터·임시 어댑터·미구현 기능은 실제 연동·검증 성공으로 표시하지 않는다.
- 비밀키·시드·인증정보는 저장소에 기록하지 않는다.

## 개발 역할·추천 순서

| 영역 | 책임 |
| --- | --- |
| Frontend | 입력·동의·제출 승인과 실제 상태 표시. 디자인 완성 후 React 구현 |
| Backend | 인증·권한, 승인 규칙 적용, 멱등 처리와 증명 작업 조정 |
| DB | 후보·확정 상태 분리, 허용 집계값·규칙 버전·처리 이력 |
| Compact·Midnight | 계산·상태 전이 검증, 최신 상태와 중복 등록 확인 |
| 가입자 월렛 | 가입자 측 키 관리와 트랜잭션 승인 |
| 모의 데이터 | 재현 가능한 운행 입력, 실제 연동과 명확한 구분 |

연결된 채팅의 추천 순서는 스택·첫 API 계약 선정 → 로그인·동의·본인 모의 계약 조회 → 규칙 초안·검토·승인 → 월렛·단일 운행 실제 증명 → 두 운행 누적 → 최종 신청·보험사 결정 → 새 클론 실행 검증이다. 첫 수직 기능으로 로그인·동의·본인 계약 조회를 제안했으며, Frontend 착수는 후속 디자인 완료 지시를 따른다. `GET /api/v1/contracts?query=...`는 시트의 후보 경로로, 확정 API 계약이 아니다.

Claude Code와 Midnight 개발 지원 도구를 함께 사용할 계획이다. GitHub에서 확인한 도구명은 **Midnight Expert**다. 사용자가 언급한 ‘엘리펀트’가 이를 뜻하는지는 미확인이며, [오픈소스 조사](MIDNIGHT_OPEN_SOURCE.md)에 후보를 정리했다.
