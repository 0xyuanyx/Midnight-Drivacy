## 변경 소유권

- 현재 `feat`의 미커밋 변경과 다른 기여자의 파일을 보존한다. 원격 통합은 분리된 작업 트리에서 먼저 수행한다. 기존 브랜치를 강제 갱신하거나 새 브랜치를 임의로 만들지 않는다.
- 프론트 디자인, 문구, 메뉴, 화면 순서, 공통 스타일, fixture 데모 흐름을 연동 편의만으로 바꾸지 않는다. 먼저 기존 화면의 입력·출력과 API 응답을 매핑한다. 실제 연동을 위해 불가피한 화면 상태 변경만 근거와 영향 범위를 기록하고 최소 수정한다.
- 프론트의 API 호출 경계·응답 검증·상태 매핑과 백엔드의 계약/인가 수정은 담당 영역을 구분한다. 공통 스키마, DB migration, 의존성/lockfile, 서버 진입점 변경은 관련 기여자의 기존 변경과 비교한 뒤 진행한다.
- 수기 Rule 입력의 데모 경로를 유지한다. LLM 문서 변환, 실제 GPS, 보험사 운영 시스템 연결을 연동 작업에 임의로 추가하지 않는다.

## API·상태 진실성

- 가입자와 보험사 모두 검증된 사용자 토큰을 사용한다. 백엔드의 현재 Privy 검증·온보딩 계약과 프론트의 OTP/미리보기 경계를 먼저 정렬한다. 인증 전 고정 토큰, 임의 사용자 ID, 실제 계약으로 둔갑한 fixture를 사용하지 않는다.
- 본인 계약·특약·Scope·평가기간을 서버 응답으로 확인한다. 요청에는 서버가 계산할 점수, Rule, State, 동의 시각을 넣지 않는다. 객체 단위 권한은 백엔드가 검사한다.
- 운행 시작·처리 요청은 각각 안정적인 `Idempotency-Key`를 사용한다. 동일 요청 재시도에서 세션·원본·operationId를 재사용한다. 종료된 수집 운행의 처리·누적 순서를 보존하며 유리한 운행만 선택해 반영하지 않는다.
- `운행 시작` 시 생성한 기록을 화면에 재생하는 것과 실제 계산·증명·체인 확정은 분리한다. `setTimeout` 또는 fixture 전이로 서버 결과를 성공 처리하지 않는다. `awaiting-wallet-approval`, `submitted`, `chain-unknown`, `chain-confirmed`, 실패·복구 상태를 구분한다.
- 확정된 누적 거리·점수·조건 충족 여부는 같은 운행의 chain-confirmed 결과와 Backend Confirmed State에서 읽는다. 증명 유효, 할인 조건 충족, 보험사의 적용 결정은 서로 다른 상태로 표시한다. 모의 이벤트를 원하는 할인 결과에 맞춰 다시 뽑거나 점수를 화면에서 계산해 확정하지 않는다.
- 과거 최종 신청을 검증할 때는 그 신청에 저장된 result commitment·nullifier·transaction ID 및 당시 체인 receipt를 함께 대조한다. 계약의 현재 `resultCommitment` 슬롯은 후속 신청으로 바뀔 수 있으므로 과거 신청의 유일한 근거로 삼지 않는다. 새 Confirmed State의 재신청 허용 여부는 Backend 정책과 DB 제약을 따른다.
- 원본 구간·salt·witness·월렛 비밀값을 보험사 응답, 일반 로그, 프론트 번들에 넣지 않는다. 원본 삭제와 저장 상태는 별도 확인한다.

## 이번 연동의 완료 판정

1. `운행 시작` 버튼 → 서버 Session 생성·조회 → 화면 재생 → 종료 → 처리 접수/상태 조회 → 확정된 첫 운행 결과 → 직전 확정 State를 사용한 두 번째 운행 결과를 동일 ID와 데이터로 추적할 수 있어야 한다.
2. 생성기의 거리·시간·이벤트와 Core 계산을 대조한다. 짧은 최소 거리, 같은 멱등 키, 중복 시작, 처리 실패, 승인 거절, 체인 결과 불명, 복구를 검증한다. 원하는 점수가 나오지 않아도 실제 계산 결과를 보인다.
3. ZK는 Claude Code의 독립 코드 검토와 로컬 컴파일·정상/변조 테스트를 각각 기록한다. 이것만으로 가입자 월렛, 체인 반영, 원격 DB migration, 브라우저/기기 종단 검증 완료를 주장하지 않는다.
4. 실제 Auth/DB/C/Wallet 연결에 필요한 설정이나 인계가 없으면 해당 단계를 미검증으로 남기고, 로컬 fixture·Stub 결과와 분리해 보고한다.

보험사 할인 적용 결정까지의 연동은 모의 운행의 확정 누적 결과와 별도 업무 단계다. 신청·심사 화면을 연결할 때는 `VERIFIED` 신청과 `APPLIED`/`REJECTED` 결정을 별도로 검증한다.
