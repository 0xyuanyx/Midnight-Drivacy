**HIGH‑1 detail.** `submitEvaluation` now reads the witness once (`driving-state.compact:355`), asserts `hashOwner(secret) == ownerBinding` (`:356`) and threads that same local into `hashEvaluation(secret, …)` (`:364`). I re-read all six circuits: `initialize/beginTrip/appendRecord/finishTrip/cancelTrip` each call `authorize()` exactly once and never use the secret again, and every other witness (`ruleOpening`, `previousOpening`, `nextOpening`, `pendingBefore`, `pendingAfter`, `recordOpening`, `inclusionPath`, `resultSalt`) is read into a single local per circuit — no second call site remains anywhere in the file. The nullifier is now `H(tag, checked_secret, s.scope, s.rule, hashState(s))` with `s.scope == scopeBinding` and `s.rule == ruleHash` asserted in `checkResult`, so it is bound to the authorized owner. `ADAPTER_PROFILE` is `…-v3-evaluation-owner` (`state-adapter.ts:13`), which does prevent conflating v2/v3 openings (`prepareTrip:194`, `prepareEvaluation:15-16`). The adversarial test at `driving-state.test.ts:245-261` alternates the witness on every second read and asserts the on-ledger nullifier equals the honestly derived one and that the repeat is rejected — it genuinely discriminates (a two-read contract would yield the alternate secret on read #2 and fail the assertion).

### Medium

- **Retry‑exhausted `TEMPORARY_FAILURE` still wedges the scope permanently at both C and B; the new abandonment path structurally excludes it** (`packages/midnight/src/trip-job.ts:211-214, 228-230, 107-110`; `apps/backend/src/chain-state/chain-finalizer.ts:159`; `packages/shared/src/bc-contract.ts:179`)
  - **Problem:** `bc-contract.ts:179` *enforces* `retryable === (code === "TEMPORARY_FAILURE")`, so a job that burned all three retries is still `retryable: true` while `retryTemporaryFailure` refuses it (`retries >= 3` → `RETRY_BLOCKED`, `:229`) and `failBeforeSubmission` can no longer re-classify it (`journal.result.status === "failed"` → `RECOVERY_REQUIRED`, `:210`). Consequences: (a) C — `TripJob.load` only exempts failures whose `code !== "TEMPORARY_FAILURE"` (`:108`), so every new `TripJob` on that scope throws `SCOPE_BUSY` forever; (b) B — `abandonJob` requires `!result.error.retryable` (`:159`), and `canAbandonTrip` requires the same (`trip-job.ts:63`), so the row stays `pending` and `chain_jobs_one_pending_scope` blocks the next `createJob` forever. This is the identical wedge as MED‑2, reached by a different terminal path (e.g. proof server or indexer down across all three backoffs at 1/5/15 min).
  - **Impact:** Availability only — no funds, no chain corruption, nothing is submitted (the wedged job has no `transactionId`). But the scope is unusable with **no in-code remedy**; recovery requires hand-editing the job journal file and the `chain_jobs` row. The new `SCOPE_BUSY` mapping (`chain-finalizer.ts:96-97`) makes the failure legible but not recoverable.
  - **Fix:** give exhaustion a non-retryable terminal code instead of leaving it `retryable`, and let both release predicates accept it:
    ```ts
    // bc-contract.ts: add "RETRIES_EXHAUSTED" to the code enum (refine already keeps retryable=false)
    // trip-job.ts — failBeforeSubmission
    const exhausted = code === "TEMPORARY_FAILURE" && journal.retries >= 3;
    const final = exhausted ? "RETRIES_EXHAUSTED" : code;
    journal.result = this.result({ status: "failed",
      error: { code: final, retryable: final === "TEMPORARY_FAILURE" } });
    ```
    `load()`'s `code !== "TEMPORARY_FAILURE"` test and `canAbandonTrip`'s `!error.retryable` test then both release the scope, and B's `abandonJob` clears the `pending` row through the path it already has. Add a unit case next to `trip-job.test.ts`'s "allows exactly three classified pre-submission retries" asserting `canAbandonTrip === true` after the fourth failure.

### Low

- **`createJob` treats an `abandoned` row as a successful idempotent replay** (`apps/backend/src/chain-state/chain-finalizer.ts:77-84`)
  - **Problem:** The early-return branch matches on `scope_key`/`request_hash`/`source_key` only; it was written when `status` could only be `pending`/`db-confirmed`. After abandonment, re-posting the same `operationId` returns success while no `pending` row exists; the driver then gets `CLAIM_UNAVAILABLE` from `claim()` or `JOB_NOT_PENDING` from `finalize()` with no indication that the job was abandoned. Fail-closed, but the new terminal state is not represented at the entry point.
  - **Fix:** `if (job.status === "abandoned") throw new FinalizationBlocked("JOB_ABANDONED");` before the `return;` at `:83`, so a retry must use a fresh `operationId`.

- **The abandon path uses unqualified table names while the rest of the file is schema-qualified** (`apps/backend/src/chain-state/chain-finalizer.ts:164, 168`)
  - **Problem:** `SELECT * FROM chain_jobs … FOR UPDATE` and `UPDATE chain_jobs SET status='abandoned'` drop the `public.` prefix used everywhere else (`:77, :85, :91, :114, :129, :141, :146, :172, :179`). Postgres resolves unqualified table names through `search_path` with `pg_temp` ahead of `public`. Not exploitable under the current wiring (the pool runs as a trusted internal role and no untrusted SQL shares the session), so this is consistency hardening on a state-transition statement, not a live bypass.
  - **Fix:** qualify both statements (`public.chain_jobs`) and, ideally, pin `SET search_path = pg_catalog, public` on pool connect.

- **A `JobBlocked` thrown by the trusted chain reader escapes `abandonJob` unmapped** (`apps/backend/src/chain-state/chain-finalizer.ts:158-159`, `packages/midnight/src/trip-job.ts:61`, `packages/midnight/src/local-job-store.ts:10-19`)
  - **Problem:** `canAbandonTrip` takes `store.withLock`, which throws `JobBlocked("STORE_BUSY")` on lock contention (and the local store's single lock file is global, `_scopeKey` is ignored). In the probe wiring (`driving-local.ts:251-252`) that exception propagates straight out of `abandonJob` as a non-`FinalizationBlocked` error — the same "raw internal error surfaces as an opaque 500" shape that the `23505 → SCOPE_BUSY` mapping was added to remove.
  - **Fix:** wrap the reader calls, e.g. `const safe = await this.chain.canAbandonTrip(id).catch(() => { throw new FinalizationBlocked("CHAIN_STATUS_UNAVAILABLE"); });`, keeping the fail-closed behaviour but as a domain error.

### Suggestions

- **The approval dialog's `Tx SHA256` is the digest of the pre-balance transaction, and `previousStateCommitment` is not shown** (`packages/midnight/browser/local-wallet-page.ts:44-45`, `wallet-runtime.ts:74-76, 86`). The LOW finding is closed: the digest is computed by the wallet itself and is exactly the value `balance()` re-checks, and `operationId`/`newStateCommitment` are explicitly labelled "어댑터가 제공한". Two residuals worth a label change: (a) the digest is over the unbalanced, pre-binding proven transaction, so it will never equal the transaction ID the user later sees on an explorer — label it as "승인 대상 Tx(잔액 처리 전) SHA256"; (b) `ApprovalDisplay.previousStateCommitment` is carried through `trip-job.ts:155` but never rendered, so the dialog shows only half of the asserted transition.

### Positive Highlights

- The HIGH fix is the minimal correct one: one witness read, checked, then reused — no helper indirection, no new constraints, and the inline comment at `:353-354` records the trust-boundary reason. All five other circuits were re-verified as single-read.
- `balance()` now consumes both `approved` and `consumedApprovalIds` in the synchronous window before the first `await` (`wallet-runtime.ts:80-86`), matching the `approve()` pattern; a digest mismatch burns the approval, which is the fail-closed direction.
- `abandonJob` is genuinely owner-gated twice (role + `owner_user_id` join at `:152-156`, then `owned()` inside the transaction at `:163`), re-reads the row `FOR UPDATE`, is idempotent (`:157`, `:165`), refuses anything not `pending`, clears the claim, and deliberately does **not** delete the unconfirmed source — `backend-local.ts:70-71` asserts source retention and that `deleteConfirmedSource` still rejects.
- `canAbandonTrip` is the strong version: it re-reads under the scope lock and requires `steps.every(step => !step.transactionId)`, so a job whose *earlier* step was submitted cannot be released even if the final error omits a `transactionId` — asserted at `trip-job.test.ts:70-76`.
- I independently confirmed the TOCTOU argument for `abandonJob`'s pre-transaction C check: from a `failed`, non-retryable, zero-`transactionId` journal, no `TripJob` method can return the job to a live state (`runStep` → `TERMINAL_JOB`, `failBeforeSubmission` → `RECOVERY_REQUIRED`, `retryTemporaryFailure` requires `TEMPORARY_FAILURE`, `recoverStep`/`rejectStep` require a `transactionId`, `confirm` requires confirmed receipts). The check does remain valid after the scope lock is released.
- The partial index is still `WHERE status = 'pending'` (`migration:29`), so `abandoned` rows correctly stop blocking the scope, and `UNIQUE (scope_key, idempotency_key)` still maps to `IDEMPOTENCY_CONFLICT` via the constraint-name branch at `:96-97`.
